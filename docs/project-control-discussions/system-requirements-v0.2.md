# System Requirements v0.2

## 1. 问题定义

目标不是做一个更复杂的 terminal 网格，也不是做一个泛化的多 agent 平台。

真正的问题是：

> 当一个复杂项目同时存在多条工作线、多个 agent、多个 runtime、跨多天执行时，如何让人始终知道：谁在做什么、为什么这么做、证据是什么、哪里有冲突、现在该不该介入。

## 2. 系统定位

建议把系统定位为：

> 一个面向复杂软件项目、agent-neutral 的项目控制台，用于组织多条工作线、调度多个 agent 与 runtime、共享代码空间与项目历史、展示时间线与证据、支持结构化互审与关键节点裁决，从而让人类在跨多天的多 agent 执行中不迷失方向。

这个定义里有几个关键词不能丢：

- `复杂软件项目`：不是泛任务平台。
- `agent-neutral`：不绑定单一 agent。
- `项目控制台`：不是 terminal 壳层。
- `多工作线`：不是单线程任务流。
- `共享代码空间与项目历史`：不只是共享聊天。
- `结构化互审与裁决`：不是 agent 群聊。

## 3. 核心目标

- 让人对项目整体保持方向感，而不是只盯某一个 session。
- 让任务成为一等对象，而不是把终端标签页当作业务主语。
- 让系统能表达证据、冲突、失败和决策，而不是只堆自然语言输出。
- 让 agent 可以连续运行，但把人保留在真正关键的判断节点上。
- 让历史可追踪、可回放、可解释。

## 4. 非目标

这些方向在当前阶段应明确排除：

- 把产品重新拉回“terminal 管理器”
- 做一个覆盖所有数字工作流的通用 agent 平台
- 用 agent 群聊取代结构化协作
- 把“完全自治”当作产品目标
- 让人类持续充当全程操作员

## 5. 需求边界的关键判断

### 5.1 哪些是准确的核心需求

- 项目级控制，而不是会话级控制
- 任务优先，而不是终端优先
- 共享代码空间是一等对象
- 跨 agent、跨 session 的项目历史是核心能力
- 人类的角色是裁决者和接管者，而不是持续操作员
- 系统需要有限自治，而不是无限自治

### 5.2 单用户假设

当前阶段的核心假设是：

- 单人类操作者（裁决者），多个 agent
- Approvals Inbox 是单人队列，不存在多人审批冲突
- 当前阶段的人类身份模型只需区分一个唯一操作者 `human`；不会出现多人类审批冲突
- 但 audit / orchestration 仍需要记录 `agent`、`orchestrator`、`system`、`policy_engine` 等非人类 actor 类型

多人类协作是未来扩展方向，不是 P0。如果后续引入多人类，需要重新设计：

- 审批权限分配
- 裁决冲突解决
- 角色与可见性控制

### 5.3 哪些地方必须收紧

- terminal 只能是任务详情里的一个执行视图，不能重新成为首页中心
- agent-neutral 不等于做成泛个人助理或全场景平台
- 协作必须围绕 `Claim -> Review -> Decision`，而不是任由 agent 互相聊天
- 自治必须受控，否则任务和 session 会无限分裂，反而放大迷航问题

## 6. 人类与系统的分工

### 系统应负责

- 规则覆盖范围内的 yes/no 决策
- 流程推进与状态迁移
- 证据收集与结构化呈现
- reviewer / verifier session 的自动派生
- checkpoint、失败、冲突的升级

### 人类应负责

- 目标重定义
- 创造性方案选择
- 高后果判断
- 最终业务验收

所有最终业务验收都必须形成显式、可审计的裁决记录，而不是只留下一个隐含状态或布尔值。

一句话收束：

> 系统负责可规则化的问题，人类负责真正需要判断力的问题。

## 7. 需求优先级

### P0：方向感层

系统首先必须让人看清：

- 项目
- 工作线
- 任务
- 当前状态
- 风险
- 待决事项

### P1：证据层

系统必须能展示：

- diff
- 测试结果
- 命令痕迹
- 关键产物
- `Claim / Review / Decision`

### P2：历史层

系统必须能保留并查询：

- 跨 agent 的 timeline
- decision history
- session 接力关系
- replay 所需事件流

### P3：执行层

系统需要统一管理：

- terminal
- runtime
- 本地与远程执行环境
- session 生命周期

但这一层不应该重新定义产品。

### P4：自治层

系统可以逐步增加：

- 自动拆子任务
- 自动开 reviewer session
- 有限并发
- 自动回退或重试

但自治是增强器，不是系统主语。

## 8. 第一阶段必须支持的用户决策场景

- 当前项目有哪些活跃工作线
- 哪些任务正在跑、被阻塞、等待人类
- 某个任务当前由哪些 session 在执行
- 某个“完成”主张背后的证据是什么
- reviewer 是否支持该主张
- 是否已经达到可验收状态
- 谁在何时基于什么证据做出了最终验收
- 是否出现冲突、失败或危险操作，应该立即介入

## 9. 产品原则

- 项目高于会话
- 任务高于终端
- 证据高于描述
- 结构化互审高于自由讨论
- 有限自治高于无限自治
- 方向感高于炫技式自动化

## 10. 当前版本的最终判断

这套需求没有跑偏，但必须始终守住下面这条主线：

> 系统的核心不是”多 agent”本身，而是让人类在复杂项目里对多工作线、多 agent、多 runtime、跨多天执行保持方向感、决策感和证据感。

## 11. 从当前 RoamBench 的迁移路径

当前 RoamBench 是一个 Go + tmux 的单用户远程终端工作台。新的控制系统不是推翻现有产品，而是在其上构建控制层。

### 概念映射

| 当前概念 | 新系统对应 | 说明 |
|---|---|---|
| tmux session | `Session` | 一个 tmux session 成为 Task 下的一个执行实例 |
| terminal tab / pane | 执行视图 | 降级为 Task Detail 页面里的一个嵌入视图 |
| workspace layout | `Project` 的 UI 层 | 布局不再是产品主语 |
| 文件浏览器 | `Artifact` 的 URI 入口之一 | 继续存在，但证据应结构化 |
| WebSocket 连接 | `Runtime` 的通信通道 | 现有 WebSocket 基础设施可复用 |

### 迁移策略

建议采用渐进式演化，而不是平行重写：

1. **第一步**：在现有 Go 后端上新增 `Project`、`Workstream`、`Task`、最小 `Event / Checkpoint` schema 的数据层和 API，前端新增项目控制台视图
2. **第二步**：把现有 tmux session 管理改造为 `Session` + `Runtime` 模型，终端视图嵌入 Task Detail
3. **第三步**：引入 `Claim`、`Review`、`Decision`、策略引擎，以及自动 `Checkpoint` 路由与审批工作流

补充说明：

- `Checkpoint` 的最小 record schema 应随数据层尽早落地，以便审批入口和审计链从第一天就存在
- 第三步新增的是自动 `Checkpoint` 路由、审批界面和 richer approval workflow，而不是第一次发明 `Checkpoint` 对象本身

现有的终端能力不会消失，而是成为 P3 执行层的基础设施。

## 12. Agent 接口契约（最小定义）

“Agent-neutral”意味着系统定义协议，agent 只需实现该协议。

### 最小契约

一个 agent 要被系统管理，必须支持以下能力：

1. **生命周期管理**
   - 可被启动（接收 task goal、scope、success criteria）
   - 可被暂停 / 恢复 / 终止
   - 可报告健康状态（heartbeat 或 health check endpoint）

2. **结构化输出**
   - 能以 `Claim` 格式提交主张（包含 claim_type、statement、confidence、evidence_refs）
   - 能以 `Artifact` 格式提交证据（diff、test result、command output）

3. **事件发射**
   - 关键动作必须发射 `Event`（状态变化、失败、阻塞）
   - 事件格式遵循系统定义的 `event_type` 枚举

### 不要求

- 不要求 agent 理解其他 agent 的输出
- 不要求 agent 自行协调
- 不要求 agent 实现 review 逻辑（系统负责派发 reviewer session）

一句话收束：

> Agent 只需要能被启动、能汇报、能被停止。协调和裁决是系统的事。
